## 1. 前提

- **目的はポートフォリオ**。少数の人がきちんと見ることを想定する。検索流入の最大化は目標にしない。OG 画像の個別化だけは行う（リンクを手渡しで共有するため）。
- **撮影は継続する**。2026-03 の実績で約 2.2枚/日。年単位で数百枚に達する前提で設計する。
- **gallery-manager はローカル専用**。Web デプロイは行わない。ただし `process.cwd()` 依存のパス解決はバグなので、website のパスは設定として外から与える。
- **既存データを壊す移行を許容する**。互換レイヤは持たない。

## 2. 実測（2026-08 時点、42オブジェクト / 6.4MiB）

| ページ | 画像枚数 | 配信バイト数 | 実際の表示サイズ |
|---|---|---|---|
| `/gallery/milltina/` | 25 | **3.72 MB** | 341px 角 |
| `/gallery/manuka/` | 11 | 1.88 MB | 同上 |
| `/gallery/kipfel/` | 5 | 0.68 MB | 同上 |
| `/gallery/`（一覧） | 3 | 534 KB | 192px 幅 |

原寸 1080×1920 または 1920×1080 を 341px 角の枠に流し込んでおり、面積比で 9〜17 倍の過剰配信。
`next.config.mjs` の `images.unoptimized: true` により `next/image` は srcset を生成しないため、既存コードの `sizes` 指定は**すべて無効**。

既存41枚のうち **29枚はファイル名に撮影日時を含み、12枚は含まない**（`milltina-01`〜、`kipfel-01`〜）。カバー専用として `images[]` の外にある `milltina-08.webp` を加えると、日時を持たないものは13枚、写真は全部で42枚（S3 のオブジェクト数と一致）。これら13枚の撮影日時は原本との知覚ハッシュ照合で特定済み（§8）。

原本のファイル名は解像度を偽ることがある。`VRChat_2026-03-11_02-58-51.207_1920x1080.png` の実サイズは 1080×1920 で、VRChat はカメラ設定側の値で命名しているとみられる。`width` / `height` をファイル名から導出してはならない。

## 3. データモデル

```
アバター (販売物)  1 ──< バリアント (調整した素体)  1 ──< 写真
```

- 写真は**必ず1つのバリアントに属する**（必須・単一）。付け替えは sidecar のディレクトリ間移動で表現する。
- カバーは**そのバリアントの写真のいずれか**でなければならない。写真と独立したカバーは持たない。
- 衣装はモデル化しない（§7）。

### ファイル配置

```
website/content/
├── avatars/
│   └── milltina.yml          # displayName, author, sourceUrl
└── gallery/
    └── milltina/             # = バリアント名。トップレベルの名前空間
        ├── _variant.yml      # avatar, displayName, coverPhotoId
        └── 2026-03-19-054345-{photoId}.yaml
```

`_variant.yml` の `avatar` は `avatars/` に実在する ID でなければならない（スキーマ検証で強制）。

### 写真の sidecar

| フィールド | 必須 | 備考 |
|---|---|---|
| `photoId` | ✅ | 不透明な短い ID。不変。URL はここから導出（ADR-0002） |
| `capturedAt` | ✅ | ISO8601。原本ファイル名 → EXIF → mtime の順で決定 |
| `width` / `height` | ✅ | Sharp が既に取得している値。CLS 防止と srcset に使う |
| `caption` | | 任意。あれば `alt` に流用し、無ければ機械生成にフォールバック |
| `dominantColor` | | Sharp の `stats().dominant`。読み込み中のプレースホルダに使う |

`alt` を独立したフィールドにしない理由、`world` / `tags` を今は持たない理由は §7。

### S3 のキー

```
gallery/{photoId}.webp          # ライトボックス用 2048
gallery/{photoId}-640.webp      # グリッド用
gallery/{photoId}-1080.webp     # 一覧カード用
gallery/{photoId}-og.webp       # OG 用 1200×630（カバーのみ生成）。切り抜かず全体を収める
```

バリアント名も撮影日もキーに含めない（ADR-0002）。原本は別バケット（非公開・Standard-IA）に `originals/{photoId}.png` として保管する（ADR-0003）。

## 4. 表示

### トップ `/gallery/`

バリアントのバナーを列挙し、アバター単位でヘッダを挟む。**バリアントが1つしかないアバターにもヘッダを出す。** 有無がデータによって変わるほうが読み手にとって一貫性を欠く、という判断による。

順序はアバター群・群内バリアントとも「最新の撮影日が新しい順」。手動順は持たない。

### バリアントページ `/gallery/{variantName}/`

- 写真を **撮影日の降順**で並べ、**月ごとに区切り**を入れる。月が1つしかない場合も区切りを出す（トップのアバターヘッダと同じ理由）。
- 並び替えは表示側の1箇所だけで行う。保存時ソート（`sortImages`）は廃止する。
- ファーストビューの数枚は `priority`、以降は `lazy`。
- ページ末尾に `Base: {アバター名} by {作者}` を出す。

配信は素の `<img>` に `srcset` / `sizes` / `width` / `height` を明示する。`next/image` は使わない（サムネイルを別ファイルで持ち URL を導出する以上、得るものが無いため）。

### メタデータ

バリアントごとに `generateMetadata` を実装し、OG 画像にカバーの `-og.webp` を指定する。

OG は 1.91:1 が固定なので、1080×1920 の縦長から切り出すと高さの3分の1しか使えず顔が必ず切れる（`attention` 戦略でも `kipfel` は目から上だけになった）。そのため**切り抜かず、写真全体を収めて背景に同じ画像のぼかしを敷く**。個別ページを sitemap に載せ、`lastModified` はそのバリアントの最新撮影日にする（現在の `new Date()` は毎日全 URL の更新日を書き換えており、クローラに恒常的に嘘を送っている）。

## 5. パッケージ構成

`packages/gallery-schema` を新設し、以下を1箇所に集約する。

- 型定義（現在 `website/src/types/gallery.ts` と `gallery-manager/src/types/content.ts` に分裂）
- URL 組み立て（現在 `website/src/lib/image-url.ts` と `gallery-manager/src/lib/image-url.ts` に同一ロジックが2つ）
- sidecar と `_variant.yml` / `avatars/*.yml` のスキーマ検証

index は**ビルド時にディレクトリを走査して組み立てる**。生成物はコミットしない。`generateStaticParams` と各ページで重複して読まないよう、モジュールスコープで1度だけ読む。

## 6. 実装順序

1. **原本の保管を開始する**（ADR-0003）。既存41枚の原本はローカルに現存しているので、まず退避する。放置した分だけ失う唯一の項目。
2. **`packages/gallery-schema` を作る**。型・URL 組み立て・スキーマ検証。
3. **マイグレーションスクリプト**。既存 `gallery.json` → sidecar 群。
   - `photoId` を採番し、S3 のオブジェクトを新しいキーへコピーする（42件）。
   - `capturedAt` は 29枚をファイル名から復元し、残り13枚は §8 の対応表から与える。
   - `milltina-08.webp` はカバー専用として `images[]` の外にあったが、**写真として取り込み**、`coverPhotoId` で指す。
   - 既存3件は「アバター1 = バリアント1」として移行する。バリアント名は現状のまま（`milltina` 等）を維持し、URL を変えない。
4. **派生物の生成**。`convertToWebP` を 640 / 1080 / 2048 / og の生成に拡張し、既存分をバックフィルする。
5. **website の書き換え**。sidecar からの読み込み、月別区切り、素の `<img>` + srcset、`generateMetadata`、sitemap。
6. **gallery-manager の書き換え**。旧構造のまま `gallery.json` を読み書きしており、
   website の切り替えと同時に機能しなくなる。sidecar の読み書き、原本の退避、
   派生物の生成とアップロードへ差し替える。`sortImages` はここで廃止される。
7. **CI の検証**。スキーマ検証、sidecar ⇔ 派生物の双方向チェック、原本 ⊇ sidecar の片方向チェック。
8. **インフラの整理**。gallery バケットを OAI/OAC 経由に閉じる。使われていない CORS 設定（`localhost:3001` への PUT/POST 許可。実際の経路はサーバー側 SDK なのでブラウザは S3 と直接通信しない）を削除する。

`sortImages` の廃止に伴い、`gallery-manager` のそのテストも削除される。

移行前の公開オブジェクト 42 件の削除は、website の切り替えが本番に出てから行う。
manifest の `legacyKey` がその一覧を持っている。

## 7. やらないと決めたこと

記録しておかないと、いずれ誰か（将来の自分を含む）が再提案する。

| | 理由 |
|---|---|
| **衣装・コーデをモデル化する** | 都度入力の運用コストに見合わない。1コーデ＝複数アイテムを表現するには entity の新設が要り、コストの桁が違う |
| **衣装作者のクレジット** | 上と同じ。アバターのクレジットだけ出す（entity が既にあるため2フィールドで済む） |
| **`world` / `tags` / 独立した `alt`** | すべて手入力。空のまま放置されるより、`caption` 1つに絞るほうが実質的 |
| **アバター単位のページ** | 作らないと決めることで、バリアントがアバター名を専有する URL 衝突が起きなくなる |
| **多軸インデックス（月別・ワールド別のページ）** | sidecar 構造なので後からビューを足すだけで実現できる。今は作らない |
| **gallery-manager の Web デプロイ** | ローカル専用と決めた。これによりメタデータを S3 に移す必要が消える |
| **`blurDataURL`（base64 LQIP）** | バンドルに載る。`dominantColor` で同等の効果がほぼタダで得られる |
| **Next.js Image Optimization / カスタムローダー** | 前者は `output: 'export'` を捨てることになる。後者はサムネイルを別ファイルで持つ設計では得るものが無い |
| **Lambda@Edge でのオンザフライリサイズ** | この規模には過剰 |
