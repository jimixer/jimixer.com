# 写真のメタデータを画像別 sidecar として git に置く

写真のメタデータは `website/content/gallery/{variantName}/{capturedAt}-{photoId}.yaml` として **1写真＝1ファイル**で保持し、git を唯一の真実とする。ビルド時にディレクトリを走査して index を組み立てるため、生成物はコミットしない。

## 検討した選択肢

- **単一 JSON（従来の `gallery.json`）**: 追加のたびに全体を読んで書き戻すため lost update が構造的に起こり、削除時にメタデータが取り残される。静的 import 経由で全ページのバンドルに載る。
- **アバター別 JSON への分割**: 上記の問題をどれ1つ解いていない（単一 JSON の延命にすぎない）。
- **S3 を真実にする（メタデータを S3 に置き、ビルド時に fetch）**: gallery-manager をローカル以外へデプロイできるようになるが、ビルドが AWS 資格情報なしに完結しなくなり、メタデータの git 履歴も失う。ローカル専用で運用する限り対価に見合わない。
- **SQLite をコミット**: クエリ性は最も高いが、git diff が読めなくなる。git を真実に選ぶ最大の動機がレビュー可能性である以上、動機ごと失われる。
- **原本の XMP/EXIF を真実にする**: 写真の世界では正統だが、原本は非公開バケットに置くためビルドのたびに取得が要り、「原本は不変」という契約（ADR-0003）とも矛盾する。

## 帰結

- 写真の追加は新規ファイルの作成のみで、既存ファイルを読み書きしない。
- 削除は sidecar を消す操作になり、「S3 に画像が残る」種類の不整合が構造的に起きにくい。
- アバター別以外の軸（月別・将来のワールド別等）を、ファイル構造を変えずにビュー側で切れる。
- ファイル数は写真数に比例して増える（数百〜千のオーダーを想定）。
